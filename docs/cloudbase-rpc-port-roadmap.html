Chronelle · deployment architecture

CloudBase rpc write port

The route from a PostgreSQL-only API to one that runs on the shared CloudBase cluster with no TCP connection: every mutation becomes a PostgreSQL function called through the gateway's rpc route, one operation family at a time, each proven equal to the Drizzle service by a differential test. The Drizzle path stays first-class, so a TCP deployment remains a configuration change.

The Drizzle implementation is never deleted or skipped in tests; functions ship as ordinary migrations that a TCP deployment carries unused. Business logic never branches on the backend.

Execution plan

STAGE 01 Done

rpc route and error contract

Prove that one gateway call runs one audited transaction before porting anything.

  • rpc() on the RDB client; CloudBaseRpcError carries the HTTP status and the gateway's prefixed SQLSTATE.
  • Custom PT403, PT409, PT422, and PT500 codes map to 403, 409, 422, and 500 on the gateway; missing and forbidden share one code so existence never leaks.
  • Staging evidence: a raise after every write persists nothing; four concurrent calls on one version produce one winner.
STAGE 02 In progress

Single-object create and update

Event, Task, Expense, and Reminder, each on the shared core with its own state rules.

  • Shared core: authorization, the objects row, the version predicate, the audit event, and the revision snapshot are implemented once; typed steps are resolved by name.
  • Per family: chronelle_assert_<type>_state with the service's messages, insert, validate, apply, serialize, and rows functions, a CloudBase<Type>WriteRepository subclass, and a differential test on the shared harness.
  • Event (migration 0012) and Task (migration 0013) merged; Expense and Reminder follow the same shape.
  • Staging run per family with CLOUDBASE_CONTRACT_FAMILY.
STAGE 03 Planned

Linked creation

The first cross-object function: a typed object and its includes relation in one transaction.

  • POST /api/events/:id/resources creates the child on the parent's scope, the relation with its version, and both audit rows.
  • Injected-failure test: a raise after the relation insert leaves no object, relation, audit, or revision row.
STAGE 04 Planned

Relations and lifecycle

Relation changes, soft deletion, trash recovery, and revision restore.

  • Include, attach, paid-for, and removed-link relations with their own version predicates.
  • Delete, restore, and revision restore keep object, relation, and recovery records consistent inside one call.
  • Differential tests compare the full ledger: objects, relations, audit, revisions, recovery.
STAGE 05 Planned

Sharing, scope, and layouts

Grants, revocation, stop-inheritance, and Event page layout history.

  • Scope changes are versioned; inherited access is recomputed from the canonical scope, never from relations.
  • Layout panels and their restore history keep optimistic concurrency and audit.
STAGE 06 Gate

Commands, undo, and redo

Durable command state and inverse operations need one transaction across the command, the object, and both ledgers.

  • Execute, undo, and redo as functions that reuse the family functions for the object change.
  • Gate: the reversible-command suites pass on both backends, and an injected failure exposes no half-applied command.
STAGE 07 Planned

Remaining reads

Move the projections still served by Drizzle behind read repositories or read functions.

  • Event detail and the to-do, timeline, itinerary, expense, and reminder projections.
  • Search as a function, since the gateway has no full-text ranking of its own.
  • Object, relation, sharing, revision, recovery, and storage inventory reads, each with its differential test.
STAGE 08 Planned

Attachments, backend mode, and operations

The API runs without DATABASE_URL, and the switch back is configuration.

  • Attachment upload, finalize, and download authorization against the storage provider with short-lived private URLs.
  • One backend mode in deployment configuration; startup verifies the required functions are installed before enabling it.
  • Metrics for gateway latency, rate limits, rejected conflicts, and function errors; versioned migration and rollback runbooks.
  • CI keeps running every suite on the Drizzle path; a TCP deployment flips the mode and changes nothing else.

What every family must satisfy

Rule Meaning How it is checked
Two implementations, one interface The Drizzle service and the CloudBase adapter both implement the family's repository; deployment configuration picks one. Both run in the differential test; the Drizzle suites stay in CI.
Same rows, same errors Resource, audit event, revision snapshot, and every error class and message match the service. Differential test over every field including clearing, command metadata, invalid states, conflict, missing, forbidden, and the missing-baseline guard.
One call, one transaction A function either commits every row or none; the API never issues a second request to complete a write. Staging rpc contract: raise after every write persists nothing; one winner in a race.
Functions are migrations Immutable NNNN_*.sql files with a checksum ledger; on staging they are applied through the console with the ledger row. Persistence test counts migrations; the harness refuses to run when the family's functions are missing.
No backend branching in business logic Services delegate to an injected repository or run their own transaction; nothing inspects a flag. Review; the flag is read only in server configuration.
