CloudBase migration roadmap

A staged route to CloudBase that preserves canonical identity, authorization, auditability, optimistic concurrency, recovery, and the existing PostgreSQL TCP option.

1 / 7phases complete
PostgreSQLcurrent runtime default
CloudBase RDBread transport available
Current gate · R1 evidence recorded The read-only differential check has run against the real gateway for a workspace member and a grant-only viewer on a synthetic staging fixture: event pages, cursor paging, calendars, isolation, and denials match PostgreSQL. R2 and R3 are proven on staging through the gateway's rpc route: an audited Event create and update run as one transaction each, stale and forbidden calls are rejected with 409 and 403, and a raise after every write persists nothing. The write path is being ported to PostgreSQL functions; PostgreSQL remains the runtime default until the first family ships.

Execution plan

PHASE 01 Done

Connectivity and boundary

Prove the CloudBase gateway path without changing application persistence.

  • Read-only gateway probe.
  • Typed RDB read transport with identifier validation.
  • Keep Drizzle/PostgreSQL TCP adapter intact.
PHASE 02 In progress

Repository contract and schema inventory

Make backend capabilities visible at the repository boundary.

  • Classify reads, single-object writes, audited mutations, and recovery workflows.
  • Define equivalent result and authorization contracts.
  • Event-list and calendar repository boundaries are in place.
  • Differential fixture exercises the actual CloudBase adapters over an in-memory RDB client and compares canonical IDs and calendar ordering.
  • RDB transport supports validated filters and deterministic ordering.
  • Read-only CloudBase calendar adapter applies workspace, inherited grant, and expiry checks.
  • Event-list adapter preserves search, period filters, sort modes, and cursor pagination.
  • Opt-in real-gateway read-contract harness checks staging behavior without mutating CloudBase data.
  • Disabled-by-default runtime flag can opt event-list and calendar reads into CloudBase while PostgreSQL keeps all writes.
  • Operation matrix records authorization, version, audit, and transaction requirements before any new repository moves.
  • Connectivity preflight shares the request-timeout budget and gives secret-safe diagnostics for expired or unauthorized keys.
  • API startup rejects expired JWT-shaped keys before enabling the opt-in CloudBase read client.
  • The event-list adapter returns root Events only, and the differential fixture is served from the PostgreSQL rows it seeds.
  • First real-gateway run completed for two principals; the transport now accepts the gateway's success shape.
  • Cursor paging verified on staging with page sizes of one and two; the harness walks every page at a configurable size.
PHASE 03 Planned

Read-path migration

Move event, calendar, search, and detail projections behind interchangeable repositories.

  • CloudBase and PostgreSQL implementations.
  • Differential canonical-ID and permission-filter tests.
  • No mutation behavior changes.
PHASE 04 Gate

Single-object writes

Only proceed if CloudBase can enforce version checks and audit guarantees.

  • Compare-and-set version predicates: proven on staging (stale write affects no row; one winner among four concurrent updates).
  • Conflict responses identical to PostgreSQL.
  • Atomic audit: proven through the gateway's rpc route. A PostgreSQL function runs as one transaction; the probe reproduces the service's audit and revision rows and a raise discards every write.
  • Decision: writes move to PostgreSQL functions invoked through rpc, one operation family at a time, each with a differential test against the TypeScript reference.
PHASE 05 Gate

Cross-object mutations and recovery

Relations, sharing, expenses, revisions, trash, restore, undo, and redo require transaction or compensation proof.

  • Reject partial state under injected failures.
  • Keep PostgreSQL TCP fallback until proven safe.
PHASE 06 Planned

Identity, attachments, and operations

Preserve centralized authorization and private storage while adding CloudBase deployment controls.

  • Server-only keys and workspace isolation.
  • Private download authorization and short-lived URLs.
  • Quota, latency, error, and rollback observability.
PHASE 07 Optional

Native TCP deployment

Use a dedicated/private PostgreSQL route if full transaction semantics remain necessary.

  • Reuse existing SQL migrations, Drizzle schema, and integration tests.
  • No canonical data-model fork.

Capability gates

Gate Question Evidence required
R1 Do CloudBase reads match PostgreSQL? Differential projection tests for IDs, relations, filtering, and permissions.
R2 Can single-object writes reject stale versions? Conflict, authorization, and audit tests.
R3 Can cross-object mutations be atomic? Transaction or compensation failure tests.
R4 Do private data guarantees survive? Attachment and workspace-isolation tests.
R5 Is the service operationally acceptable? Staging load, latency, quota, monitoring, and rollback report.
